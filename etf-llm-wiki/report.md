## 3. 哪個節點最容易出錯？

**本次實際發生的內容錯誤在逐頁稿／內容忠實度檢查節點。**來源筆記原本記錄配息不保證，但 HTML 簡報沒有明確保留警語，產生「重要限定語在摘要轉成簡報時遺失」的風險。

另一個實際問題是**印表渲染節點**：第 6 頁比較表格在 PDF 列印版面變成兩頁，修正印表 CSS 後才恢復 10 頁。這是版面問題，無須回到 Wiki 重新整理 ETF 來源。

因本次只經過一次集中實測，**不能聲稱已統計出某個節點「出錯頻率最高」**；以上是本次已觀察到的問題節點，並非重複運行數十次的頻率比較。

## 4. 把檢查提前到哪個步驟？

原先在產生 HTML 之後才用靜態檢查發現缺少「配息不保證」。修改後，在**逐頁稿完成 → HTML 渲染之前**新增 `scripts/validate_draft.py`，先確認：

1. 至少 5 篇來源且來源編號可追溯。
2. 每張證據卡有實際登錄的來源。
3. 每頁簡報有 evidence IDs。
4. 主動式／被動式概念有對應證據卡。
5. 配息頁明確提醒「配息不保證」。

只要未通過，退回逐頁稿或證據卡；不啟動 HTML 渲染。

## 5. 有沒有修改 workflow / graph？為什麼？

**有。**原本的「證據卡 → 大綱／文稿 → HTML → 測試」改為「證據卡 → 大綱／文稿 → **前置內容關卡** → HTML → 程式／列印檢查」。理由是**錯誤越早被抓到，修正成本越低**；不應讓渲染節點自行編造或修復金融事實。

我們仍採用 **Graph 決定階段、Loop 局部修正**，而不是讓 AI 每次都重做全站。修正上限為 3 輪，資料不足或重要金融資訊無法核實就停止並保留紀錄。

## 7. 心得

本次作業最重要的收穫是：AI 生成的內容看起來流暢，並不代表每個限定語都有保留。把「證據與出處」獨立成檔案、在轉成 HTML 以前做內容關卡，再把畫面問題留給渲染節點處理，可以讓錯誤在最接近源頭的地方被發現。真正可信的流程需要保留可執行的檢查與誠實的失敗紀錄，而不是只要求 AI 「再檢查一次」。
